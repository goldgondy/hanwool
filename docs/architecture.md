# 서비스 아키텍처 (서버 저장 · 세무대리형)

상태: 초안 · 작성일 2026-09-29

## 1. 목표와 전제

- 가상자산 투자자(고객)가 지갑·거래소를 연결하면, 세무사가 검토·분류를 확정하고 세액을 계산해 신고를 대리한다.
- 고객 데이터는 **서버에 저장**한다 (로그인·권한으로 보호, 민감 정보는 암호화).
- 목표 규모: **사용자 1만 명 이상.** 처음부터 여러 고객·여러 담당자를 전제로 설계한다.
- 첫 출시(2026년 12월): 고객이 계정을 연결하고 **2026-12-31 보유 잔고가 자동 기록**되는 기능. 세무사 검토·신고 기능은 2027년.

## 2. 사용자와 권한

| 역할 | 할 수 있는 일 |
|---|---|
| 고객 | 가입, 수임 동의, 지갑·거래소 연결, 내 원장·잔고 보기, 세무사 질문에 답하기 ("이 입금은 어디서 왔나요?") |
| 세무사 (관리자) | 전체 고객 목록, 고객별 원장·분류 검토·확정, 정책 설정, 세액 계산, 신고 자료 출력 |
| 직원 (선택) | 세무사가 배정한 고객만 검토 |

- 모든 데이터는 **고객 단위로 격리**한다. 한 고객이 다른 고객의 데이터를 볼 수 있는 경로가 없어야 한다 (DB 조회에 항상 고객 ID 조건, 서버에서 권한 확인).
- 세무사가 고객 데이터를 볼 때마다 **접근 기록**을 남긴다.

## 3. 전체 구조

```
[브라우저: 고객 / 세무사]
        │ HTTPS, 로그인 세션
        ▼
[웹 서버: Next.js · Vercel 서울 리전]
   ├─ 화면 (고객용, 세무사용)
   ├─ API (권한 확인 → DB)
   └─ 작업 등록 (동기화 요청)
        │
        ▼
[작업 큐 · 백그라운드 워커]              [외부 데이터]
   ├─ 계정 동기화 (원장 수집) ─────────▶  거래소 API (바이낸스·OKX…)
   ├─ 잔고 대사                          블록체인 인덱서 (유료 API / 자체 노드)
   ├─ 연말 잔고 자동 기록 (12/31 23:59)   시세 (업비트·바이낸스·환율)
   └─ 시세 캐시 채우기
        │
        ▼
[PostgreSQL]
   사용자·고객·수임 · 계정(Secret 암호화) · 원장 · 분류 결정 · 스냅샷 · 시세 캐시 · 접근 기록
```

지금 만든 로직은 대부분 그대로 쓴다. 브라우저에서 돌던 코드를 서버(워커)에서 돌리도록 옮긴다.

| 기존 모듈 | 새 위치 | 변경 |
|---|---|---|
| 수집 (EVM·BTC·거래소) | 워커 | 브라우저 → 서버 실행. 바이낸스 중계 서버는 불필요 (서버가 직접 호출) |
| 원장·대사 | 워커 + DB | IndexedDB → PostgreSQL |
| 분류기·과세 변환·세액 엔진 | 서버 (순수 함수 그대로) | 변경 없음 |
| 시세 | 서버 | 변경 없음 (이미 서버) |
| Secret 암호화 (vault) | 서버 | 사용자 비밀번호 → 서버 암호화 키 (§5) |

## 4. 데이터 모델 (주요 테이블)

| 테이블 | 내용 |
|---|---|
| `users` | 로그인 계정 (소셜 로그인 ID, 이메일, 역할) |
| `clients` | 납세자 (이름, 연락처, 담당 세무사·직원). 한 사용자가 여러 납세자를 둘 수도 있게 분리 |
| `engagements` | 수임 계약·동의 (동의 일시, 범위, 과세연도) |
| `sources` | 연결 계정 (종류, 주소·xpub, **암호화된 API Secret**) |
| `ledger_entries` | 원장 (현재 `LedgerEntry`와 같은 구조 + `client_id`) |
| `decisions` | 분류 결정 (결정한 사람: 고객/세무사, 시각) |
| `snapshots` | 잔고 기록 (12/31 자동 기록 포함) |
| `sync_jobs` | 동기화 작업 상태·오류 |
| `prices_minute`, `prices_hourly`, `fx_usdkrw_daily` | 시세 캐시 (이미 있음) |
| `audit_log` | 누가 언제 어떤 고객 데이터를 봤는지·바꿨는지 |

규모 예상: 고객 1만 명 × 평균 원장 2,000건 = 약 2,000만 행. PostgreSQL 한 대로 충분하다 (`client_id` 기준 인덱스).

## 5. 보안

- **API Secret**: 봉투 암호화. 데이터 키로 AES-GCM 암호화하고, 데이터 키는 클라우드 KMS의 마스터 키로 암호화한다. DB가 유출되어도 KMS 없이는 복호화할 수 없다.
- **거래소 키는 읽기 전용만 받는다.** 등록할 때 권한을 확인해 출금·거래 권한이 있으면 거부한다.
- xpub, 지갑 주소, 원장도 재산 정보이므로 DB 저장 시 암호화(디스크 암호화 + 민감 컬럼 암호화)를 적용한다.
- 세무사·직원 계정은 2단계 인증 필수.
- 접근 기록(`audit_log`)은 수정·삭제할 수 없게 둔다.

## 6. 외부 데이터 (규모에 따른 비용)

사용자 1만 명이 동기화하면 공개 무료 API는 서버 IP 차단으로 쓸 수 없다 (테스트 중 mempool.space에서 실제로 차단됨).

| 데이터 | 초기 (수백 명) | 1만 명 이상 |
|---|---|---|
| 비트코인 | mempool.space 공개 + 대체 서버 | 자체 노드 (Bitcoin Core + Electrs/mempool), 월 수십 달러 서버 |
| EVM | Blockscout 공개 | 유료 인덱서 (Blockscout PRO, Etherscan, Alchemy 등) 또는 자체 인덱서 |
| 시세 | 업비트·바이낸스 공개 (캐시로 호출 최소화) | 동일 (시세는 사용자 수와 무관하게 캐시가 공유됨) |

- 동기화는 **작업 큐로 속도를 조절**한다 (외부 API별 초당 호출 한도 준수, 재시도, 실패 시 알림).
- 증분 동기화 (마지막 블록 이후만)를 기본으로 해 호출량을 줄인다.

## 7. 개인정보·법규 (세무사 판단 필요)

- 개인정보 처리방침, 수집·이용 동의, 제3자 제공(세무사·국세청) 동의
- **국외 이전**: Neon(현재 DB)은 싱가포르 리전이다. 국내 보관이 필요하면 서울 리전이 있는 DB(AWS RDS 서울, Supabase 서울 등)로 옮긴다.
- 세무사회 규정: 온라인 플랫폼을 통한 수임·광고 제한 여부
- 보관 기간: 세무 자료 보관 의무 기간과 탈퇴 시 삭제 범위
- 규모가 커지면 ISMS 인증 의무 기준 확인

## 9. 결정 사항 (2026-09-29)

| 항목 | 결정 |
|---|---|
| 로그인 | 카카오, 구글, 네이버, 이메일 링크 |
| 계정 연결 주체 | 고객 직접 연결이 기본, 사무실이 대신 연결도 가능 (누가 연결했는지 기록) |
| DB 위치 | **서울 리전** (Supabase 서울 `ap-northeast-2`의 PostgreSQL). Neon 싱가포르의 시세 캐시도 이전 |
| 외부 데이터 예산 | 초기엔 공개 API + 캐시, 사용자가 늘면 월 10~50만 원 수준 유료 API·자체 노드로 전환 |

기술 선택 (개발 판단):

| 항목 | 선택 | 이유 |
|---|---|---|
| DB 접근 | Drizzle ORM + postgres 드라이버 | SQL에 가깝고 가벼움, 스키마를 코드로 관리 |
| 인증 | 카카오·네이버를 기본 지원하는 인증 라이브러리 (구현 시 최신 버전 확인 후 확정) | 소셜 로그인 4종 + 세션 DB 저장 |
| 이메일 발송 | 트랜잭션 메일 서비스 (Resend 등) | 이메일 링크 로그인, 알림 |
| Secret 암호화 | 1단계: 서버 마스터 키(환경변수)로 봉투 암호화 → 2단계: AWS KMS 서울 | 출시 전 KMS 전환 |
| 백그라운드 작업 | DB 기반 작업 큐 + 주기 실행 (구현 시 확정) | 동기화·12/31 일괄 기록 |
