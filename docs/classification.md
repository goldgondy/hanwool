# 거래 분류 체계 설계

상태: 확정 (정책 §6 결정 반영) · 작성일 2026-09-29

## 1. 목적

원장(`LedgerEntry`)은 "어느 계정에서 무엇이 얼마나 들어오고 나갔다"는 **사실**만 기록한다.
세금을 계산하려면 각 거래가 세법상 **무엇이었는지**(내 계정 간 이체인지, 교환인지, 남에게 준 것인지)를 정해야 한다.
이 문서는 그 이름표(분류)의 목록, 자동으로 붙이는 규칙, 사용자 결정을 보관하는 방법을 정한다.

```
원장(사실) ──▶ 연결(매칭) ──▶ 분류(의미) ──▶ 평가(원화) ──▶ 계산(엔진) ──▶ 보고
                                ▲
                          사용자 결정 (별도 저장, 재동기화해도 유지)
```

## 2. 분류 단위

- **그룹 단위로 분류한다.** 그룹은 원장의 `groupId`로 묶인 항목들(트랜잭션 하나, 거래소 주문 하나)이다.
  예: 스왑 트랜잭션 = USDC 출금 + ETH 입금 + 가스비 → 그룹 하나, 분류 "교환".
- **계정을 넘는 이체는 두 그룹을 하나로 묶는다.** 바이낸스 출금 그룹과 Sparrow 입금 그룹이 같은 이체라면
  둘을 연결한 "이체 쌍"이 분류 단위가 된다.
- 수수료 항목은 항상 자기 그룹의 분류를 따라가며, 세금 처리는 수수료 정책(§6)을 따른다.

## 3. 분류 목록

| 분류 | 코드 | 예시 | 세금 처리 (엔진 이벤트) |
|---|---|---|---|
| 내 계정 간 이체 | `internal_transfer` | 바이낸스 → Sparrow | 없음. 원가 유지. 수수료만 처리 |
| 코인 교환 | `trade` | USDC → ETH 스왑, 바이낸스 BTC/USDT 매매 | 판 코인 `dispose` + 산 코인 `acquire` (같은 원화 가치) |
| 법정화폐로 매수 | `buy_fiat` | 업비트 원화로 BTC 매수 | `acquire` (지불 원화 = 취득가) |
| 법정화폐로 매도 | `sell_fiat` | 업비트 BTC 원화 매도 | `dispose` (받은 원화 = 양도가) |
| 보상·이자 | `reward` | 스테이킹 보상, Earn 이자 | `acquire` (취득가는 정책 §6) |
| 에어드랍 | `airdrop` | 프로젝트 토큰 무상 지급 | `acquire` (취득가는 정책 §6) |
| 래핑·브릿지 | `wrap` | ETH ↔ WETH, 체인 간 브릿지 | 정책 §6 (기본: 이체로 보아 원가 유지) |
| 외부에서 받음 | `external_in` | 친구에게 받음, 장외 매수, 연결 안 한 지갑에서 옴 | `acquire` (취득가는 사용자 입력 필요) |
| 외부로 보냄 | `external_out` | 결제, 선물, 연결 안 한 지갑으로 보냄 | `dispose` (양도가 = 당시 시가) 또는 사용자가 이체로 변경 |
| 수수료만 | `fee_only` | approve, 실패한 트랜잭션, BTC UTXO 통합 | 수수료만 처리 (정책 §6) |
| 스팸 | `spam` | 요청하지 않은 토큰 | 무시 (원장·대사에서도 숨김 가능) |
| 미지원 DeFi | `defi_unsupported` | LP 예치, 대출 담보 | 검토 필요. 앱이 아직 해석하지 못함 |
| 미분류 | `unknown` | 규칙으로 판단 못 함 | 검토 필요 |

## 4. 분류 상태

각 그룹의 분류에는 누가 어떻게 정했는지를 함께 기록한다.

| 상태 | 의미 | 사용자 검토 |
|---|---|---|
| `confirmed` | 데이터상 확실 (거래소 체결 기록, 양쪽 원장의 같은 트랜잭션 해시) | 불필요 |
| `suggested` | 규칙으로 추정 (스팸 의심, 브릿지 추정 등) | 권장 |
| `needs_review` | 판단 불가 또는 사용자 입력 필요 (외부 입금의 취득가 등) | **필수** |
| `user` | 사용자가 직접 정함 | 불필요. 자동 규칙보다 항상 우선 |

## 5. 자동 분류 규칙

위에서부터 차례로 적용하고, 처음 맞는 규칙의 결과를 쓴다. 사용자 결정(`user`)이 있으면 규칙을 적용하지 않는다.

| 순서 | 규칙 | 결과 | 상태 |
|---|---|---|---|
| R1 | 거래소가 제공한 체결 기록 (코인/코인) | `trade` | confirmed |
| R2 | 거래소 체결 기록 (원화 등 법정화폐 포함) | `buy_fiat` / `sell_fiat` | confirmed |
| R3 | 거래소 보상 기록 (Earn 이자, 스테이킹 분배) | `reward` | confirmed |
| R4 | **그룹의 수수료 외 항목이 자산별로 합계 0** — 같은 트랜잭션이 내 두 계정에 반대 부호로 나타나거나(지갑 A → 지갑 B), 한 계정 안에서 자기 자신에게 보낸 경우 | `internal_transfer` | confirmed |
| R5 | 상대 주소가 사용자의 다른 계정 주소 목록에 있음 (상대 계정의 해당 체인을 동기화하지 않은 경우) | `internal_transfer` | confirmed |
| R6 | 수수료 항목만 있음 (approve, 실패한 트랜잭션, UTXO 통합) | `fee_only` | confirmed |
| R7 | 알려진 래핑 컨트랙트 (WETH, WBTC 발행 등) | `wrap` | confirmed |
| R8 | 알려진 브릿지 컨트랙트로 출금 + 다른 체인 내 계정에 비슷한 금액 입금 (시간 창 이내) | `wrap` | suggested |
| R9 | 한 그룹에서 서로 다른 자산이 나가고 들어옴 | `trade` | suggested (DEX 스왑) |
| R10 | 토큰 컨트랙트가 직접 보낸 입금, 시세 없음, 또는 알려진 스팸 목록 | `spam` | suggested |
| R11 | 거래소 출금 ↔ 지갑 입금이 해시 없이 금액·시간만 일치 | `internal_transfer` | suggested |
| R12 | 나머지 입금 | `external_in` | needs_review (취득가 입력) |
| R13 | 나머지 출금 | `external_out` | needs_review |

R4는 체인 데이터로 결정적이라 가장 신뢰도가 높다. 같은 체인의 내 지갑끼리 이동은 모두 R4 또는 R5로 확정된다.

## 6. 정책 (세무사 확인 대상)

법 해석이 정해지지 않은 부분은 코드에 박지 않고 정책 값으로 둔다.

| 정책 | 선택지 | 현재 값 |
|---|---|---|
| 코인으로 낸 수수료 | 즉시 손실 인식 / 원가에 얹기 | **즉시 손실 인식** (2026-09-27 결정) |
| 의제취득가 적용 범위 | 시행일 이전 보유분 / 전체 | **시행일 이전 보유분** (2026-09-27 결정) |
| 보상·이자의 취득가 | 수령 시점 시가 / 0원 | **0원** (2026-09-29 결정) |
| 에어드랍의 취득가 | 수령 시점 시가 / 0원 | **0원** (2026-09-29 결정) |
| 래핑·브릿지 | 원가 유지 (비과세 이체) / 교환으로 보아 과세 | **비과세, 원가 유지** (2026-09-29 결정) |
| 외부로 보낸 코인의 기본 처리 | 양도 (시가) / 사용자가 정할 때까지 계산 보류 | **양도로 계산하고 "미확인" 표시** (2026-09-29 결정) |

## 6-1. 원화 평가 기준

| 순위 | 기준 | 적용 |
|---|---|---|
| 1 | 실제 주고받은 금액 | 스테이블코인과의 교환 (2,000 USDC로 ETH 매수 → ETH 취득가 = 2,000 USDC의 원화 가치). 거래소 체결 기록 (연동 후) |
| 2 | 거래 직전에 마감된 **1분** 캔들 종가 | 그 밖의 교환, 외부 입출금 |
| 3 | 거래 직전에 마감된 1시간 캔들 종가 | 1분 데이터가 없을 때 |

- 출처: 업비트 KRW 마켓 → 없으면 바이낸스 USDT 마켓 × 원/달러(업비트 KRW-USDT, 없으면 ECB 기준 환율)
- 거래 이후의 가격은 쓰지 않는다.
- **세무사 확인**: 소득세법상 "거래 시점의 시가"를 어떤 가격(특정 사업자 공시가, 평균 등)으로 정하는지.

## 7. 사용자 결정 저장

- 새 테이블 `decisions`에 **원장과 따로** 저장한다. 원장은 재동기화 때 다시 만들어질 수 있지만 결정은 유지되어야 한다.
- 결정은 원장 `groupId`(또는 이체 쌍 ID)를 키로 가진다. `groupId`는 원본 데이터(트랜잭션 해시, 주문 ID)에서 만들어져 재동기화해도 바뀌지 않는다.
- 재동기화 후 대상 그룹이 사라진 결정은 "고아 결정"으로 표시해 사용자에게 알린다.

```ts
interface Decision {
  key: string;              // groupId 또는 이체 쌍 ID
  category: Category;       // §3 분류 코드
  costKrw?: string;         // external_in, reward 등의 취득가 (사용자 입력)
  proceedsKrw?: string;     // external_out의 양도가 (시가 대신 쓸 때)
  note?: string;            // "친구 A에게 선물" 등
  decidedAt: number;
}

interface Classification {  // 규칙 + 결정을 합친 결과 (저장하지 않고 매번 계산)
  key: string;
  category: Category;
  status: "confirmed" | "suggested" | "needs_review" | "user";
  rule?: string;            // "R4" 등, 왜 이렇게 분류했는지
  linkedKeys?: string[];    // 이체 쌍의 상대 그룹
}
```

## 8. 사용자 화면

- **검토 목록**: `needs_review`와 `suggested`를 원화 금액이 큰 순서로 보여 준다. 금액이 큰 것부터 처리해야 세액 정확도가 빨리 올라간다.
- 각 항목에서 분류를 바꾸고, 필요하면 취득가와 메모를 입력한다.
- **일괄 처리**: "이 주소에서 온 입금 전부 = 내 계정 간 이체", "이 토큰 = 스팸" 같은 규칙을 사용자가 추가할 수 있다.
- 세액 리포트에는 검토가 남은 항목 수와 그 금액 합계를 함께 보여 준다. ("미확인 거래 3건, 약 120만 원")

## 9. 구현 순서

1. `Category`, `Decision`, `Classification` 타입과 `decisions` 테이블
2. 분류기: 원장 + 결정 → 분류 결과 (순수 함수, 테스트 가능). 우선 R4, R5, R6, R9, R10, R12, R13
3. 검토 목록 화면
4. 분류 결과 → 엔진 이벤트 변환 (원화 평가 단계와 함께)
5. 거래소 내역 수집 시 R1–R3, 브릿지·래핑 목록으로 R7–R8, 해시 없는 매칭 R11

## 10. 열린 질문

- §6의 정책 결정과 §6-1 시가 기준 (세무사 확인)
- DeFi(LP, 대출, 리스테이킹)를 어느 수준까지 자동 해석할지
- 여러 사람이 함께 쓰는 지갑, 법인 계정은 범위 밖으로 둘지
